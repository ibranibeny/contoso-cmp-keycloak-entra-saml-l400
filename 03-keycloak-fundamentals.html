Keycloak in depth: realm, clients, keys and sessions

The Keycloak objects behind Contoso CMP, how the realm is hardened on an Azure VM, and why one Keycloak session serves both OIDC and SAML.

Level 400Keycloak 26.xOIDC + SAML~15 min

What Keycloak is, in this design#

Keycloak is an open-source identity and access management server that supports OpenID Connect, OAuth 2.0 and SAML 2.0, with realms, clients, users, sessions and protocol mappers as its core objects (Keycloak Server Administration Guide). Here it plays two roles at once in the realm cmp-pdf:

RoleClient in realmProtocolConsumer
OpenID Providercmp-frontend (confidential, standard flow, PKCE S256)OIDCCMP frontend (Container Apps)
SAML identity providerhttps://login.microsoftonline.com/aaaabbbb-0000-cccc-1111-dddd2222eeee/SAML 2.0Microsoft Entra ID (Contoso tenant)

Both clients share the realm's users, sessions and keys. That is why a person who already signed in to CMP may not see the Keycloak password page again when Entra sends them to Keycloak — the Keycloak SSO session is reused. Entra's own policies (consent, MFA, Conditional Access) still run afterwards.

Running Keycloak in production mode on a VM#

The VM runs the official image pinned by digest, in start (production) mode, listening on loopback HTTP behind Caddy. Hostname and proxy settings follow Keycloak's guides (hostname) (reverse proxy); the database is PostgreSQL over TLS with full certificate verification (database).

Container runtime configuration (secrets read from Key Vault via managed identity)Python bootstrap/sso-keycloak.py
def serve(config):
    runtime = Path("/run/cmp-sso")
    runtime.mkdir(mode=0o700, exist_ok=True)
    ca = get_secret(config["vault_uri"], "postgres-ca")
    (runtime / "ca.crt").write_text(ca)
    os.chmod(runtime / "ca.crt", 0o644)
    values = {
        "KC_DB": "postgres", "KC_DB_USERNAME": "keycloak_app",
        "KC_DB_URL": f"jdbc:postgresql://{config['host']}:5432/keycloak?sslmode=verify-full&sslrootcert=/mnt/postgres-tls/ca.crt",
        "KC_DB_PASSWORD": get_secret(config["vault_uri"], "keycloak-db-password"),
        "KC_BOOTSTRAP_ADMIN_USERNAME": "cmpbootstrap",
        "KC_BOOTSTRAP_ADMIN_PASSWORD": get_secret(config["vault_uri"], "keycloak-admin-password"),
        "KC_HTTP_ENABLED": "true", "KC_HTTP_HOST": "127.0.0.1", "KC_HOSTNAME": config["origin"],
        "KC_HOSTNAME_STRICT": "true", "KC_PROXY_HEADERS": "xforwarded",
        "KC_PROXY_TRUSTED_ADDRESSES": "127.0.0.1/32", "KC_HTTP_MANAGEMENT_HOST": "127.0.0.1",
        "KC_HEALTH_ENABLED": "true", "KC_METRICS_ENABLED": "false",
        "JAVA_OPTS_KC_HEAP": "-Xms512m -Xmx1536m"}
    if any("\n" in value or "\r" in value for value in values.values()):
        raise ValueError("Invalid environment material")
    env = runtime / "keycloak.env"
    env.write_text("".join(f"{key}={value}\n" for key, value in values.items()))
    os.chmod(env, 0o600)
    subprocess.run(["docker", "rm", "-f", "cmp-sso-keycloak"], capture_output=True, check=False)
    os.execvp("docker", ["docker", "run", "--rm", "--name", "cmp-sso-keycloak", "--network", "host",
                         "--log-driver", "none", "--env-file", str(env),
                         "--mount", f"type=bind,src={runtime}/ca.crt,dst=/mnt/postgres-tls/ca.crt,readonly",
                         IMAGE, "start"])

KC_BOOTSTRAP_ADMIN_USERNAME/PASSWORDTemporary bootstrap admin used by the installer over loopback; replace it with an approved administration method before production (Keycloak documents these variables for creating the initial admin remotely (Keycloak docs)).

Keys and certificates#

When a realm is created Keycloak generates a key pair and self-signed certificate; it uses one active key for new signatures and can keep passive keys for verification. Keycloak recommends rotating regularly — for example new keys every three to six months, deleting old ones one to two months later (Keycloak: rotating keys). For a SAML trust with Entra, every rotation changes the certificate Entra must trust, so rotations are change-managed events (G9).

Least-privilege administration#

CMP's user-administration backend never receives the master or bootstrap credential. It uses a dedicated service client whose token is checked on every use: issuer, client, expiry, and only the realm-management roles query-users, view-users, manage-users (and optionally query-groups).
