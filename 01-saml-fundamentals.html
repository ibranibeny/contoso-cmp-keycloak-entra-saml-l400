Concept 1

SAML 2.0 in depth, as used by Contoso CMP

Roles, metadata, bindings, the assertion Keycloak sends to Entra, and the validation rules that decide whether a guest gets in.

Level 400OASIS SAML 2.0Entra required claims~15 min

Why SAML 2.0 appears in this design#

CMP itself speaks OpenID Connect to Keycloak. SAML enters only because of Azure: Microsoft Entra ID can federate a workforce tenant with an external identity provider that speaks SAML 2.0 or WS-Federation, so that people from that IdP sign in to Contoso's resources as B2B users (Learn: Add federation with SAML/WS-Fed identity providers). Keycloak can act as a SAML 2.0 identity provider for any registered SAML client (Keycloak: creating a SAML client). So the SAML trust is the bridge between a Keycloak identity and an Entra guest identity.

A SAML trust is nothing more than each side holding the other side's identifier, endpoints and (for the IdP) signing certificate. Keycloak publishes its half as metadata at /protocol/saml/descriptor; Entra's half is a set of fixed values documented by Microsoft. The required Entra-side values are a tenant-specific Audience https://login.microsoftonline.com/<tenant ID>/ and the ACS https://login.microsoftonline.com/login.srf (Learn: Table 1, required attributes).

ℹTenant-specific audience

Microsoft notes that the Issuer in the SAML request Entra sends for external federations is now the tenanted endpoint. Existing federations that expect the global urn:federation:MicrosoftOnline keep working, but new federations stop working if the IdP expects the global value (Learn). This is why the Keycloak SAML client ID is the tenant URL with its trailing slash.

Messages and bindings#

SAML web SSO uses two protocol messages: the SP's <AuthnRequest> and the IdP's <Response>, which carries one or more <Assertion> elements (OASIS SAML 2.0 Core). A binding says how a message travels (OASIS SAML 2.0 Bindings):

BindingHow it travelsWhere it is used here
HTTP-RedirectDEFLATE-compressed, base64-encoded, URL-encoded in the query string (SAMLRequest, optional RelayState, signature parameters).Entra → Keycloak AuthnRequest via the browser. The metadata validator requires the Redirect SSO endpoint to be exactly the realm's /protocol/saml (G3).
HTTP-POSTBase64-encoded in an auto-submitting HTML form (SAMLResponse).Keycloak → Entra response to login.srf. The Keycloak client forces POST binding.
HTTP-Artifact / SOAPA reference is passed, the message is fetched back-channel.Advertised in Keycloak metadata; not used by this trust.

Keycloak recommends POST over Redirect for responses: a Redirect response would sit in the URL (and in logs), and URLs limit the size of the document (Keycloak: SAML bindings).

◷PoC item — not yet proven

Microsoft documents the values Entra sends (tenanted Issuer, unsigned request) but not every attribute of the AuthnRequest (for example whether it carries NameIDPolicy or AssertionConsumerServiceURL). Capture a real request in the PoC (G8) before relying on any optional attribute.

NameID: why persistent, and what it is not#

FormatMeaningUse here
persistentOpaque, stable identifier for this user at this SP; not reassigned.Required by Entra. Keycloak is forced to this format for the Entra client.
transientOne-time identifier, changes every session.Not acceptable to Entra.
emailAddress / unspecifiedEmail or IdP-defined string.Not used as NameID. Email travels as an attribute instead.
!Three identifiers, not one

The persistent NameID that Keycloak issues to Entra, the Keycloak OIDC sub that CMP sees, and the Entra guest's object ID are three different identifiers. Do not assume any two are equal, and do not link accounts by matching email text. CMP binds a Keycloak subject to an approved Entra object ID explicitly in its project catalog (see Concept 4).

Signing, certificates and rollover#

  • Keycloak signs with the realm's active RSA key; the matching X.509 certificate is published in metadata under KeyDescriptor use="signing". Keycloak keeps one active key pair and can hold passive keys to validate older signatures (Keycloak: realm keys).
  • Entra stores the certificate in the federation configuration. If you give Entra a metadata URL, it can renew the certificate automatically when it expires; if the certificate is rotated before expiry, or there is no metadata URL, you must update it manually (Learn: signing certificate expiration).
  • The Graph resource describes the auto-rollover: Entra tries to fetch a new certificate from metadata 30 days before expiry, then checks daily (Learn: samlOrWsFedExternalDomainFederation).
  • The PoC realm certificate is self-signed with ten-year validity, so automatic renewal will not trigger for years. Any planned rotation is a manual, coordinated change — see G9.

Request signing

Entra does not sign the authentication requests it sends to a federated SAML IdP: "the Microsoft Entra SAML/WS-Fed federation feature doesn't support sending a signed authentication token to the SAML identity provider" (Learn). Keycloak's realm metadata still advertises WantAuthnRequestsSigned="true"; enforcement is per client, and the Entra client sets Client signature required = Off.

◷PoC item — not yet proven

Confirm during the end-to-end test that Keycloak accepts Entra's unsigned request for this client (no 'invalid signature' on the Keycloak side).
