Transcript#

English transcript

Intro

  1. This walkthrough builds the SAML 2.0 trust that lets a Keycloak user sign in to Azure as a Contoso B2B guest.
  2. Contoso is fictitious. PoC screens are sanitized captures; illustrative screens are labelled as such.

How the connection works

  1. There are two trusts. Trust A: the CMP frontend signs users in with Keycloak over OpenID Connect.
  2. Trust B is what this video builds: Microsoft Entra ID trusts Keycloak as a SAML 2.0 identity provider.
  3. No token forwarding: CMP only opens a tenant-scoped portal link. Entra authenticates the guest itself, through Trust B.
  4. First time only: the guest opens the invitation. Its redirect URL carries domain_hint = the Keycloak Issuer URI.
  5. Because the IdP is Domainless, Entra routes by that Issuer URI and does not check the email domain.
  6. Every sign-in: the guest opens the Azure portal with the Contoso tenant in the URL.
  7. Entra redirects the browser to the Keycloak SAML endpoint with an AuthnRequest. Its Issuer is the tenant URL; it is not signed.
  8. Keycloak finds the client whose ID equals that Issuer, then reuses its SSO session or asks the user to sign in.
  9. It builds the assertion: persistent NameID, the email claim, and the Contoso tenant as the audience.
  10. Keycloak returns an auto-POST form; the browser posts the signed SAMLResponse to login.microsoftonline.com/login.srf.
  11. Entra validates signature, issuer, audience, recipient and time, then finds the guest through its external IdP association.
  12. On first use Entra shows consent, then MFA registration or challenge in the Contoso tenant, and Conditional Access.
  13. Entra issues tokens for the portal, and Azure RBAC decides what the guest can see.

Step 1 · Deploy Keycloak on Azure

  1. Step 1: deploy-sso.ps1 works in phases. Validate -Offline compiles the seven SSO Bicep templates: no sign-in, no cloud calls.
  2. Validate then checks the account, resource providers, VM SKU and quota in Indonesia Central. It is read-only.
  3. Apply asks for confirmation, then creates the isolated SSO resources in rg-cmp-sso-indonesia-poc.
  4. Verify proves HTTPS, the issuer and the SAML metadata URL. identityLogin stays NOT VERIFIED: that needs a real sign-in.
  5. PoC capture: the Keycloak VM runs Ubuntu 24.04 on a Standard D2s v5 in Indonesia Central.
  6. The PoC used this Azure DNS label for HTTPS; this guide writes the Keycloak origin as sso.contoso.com.
  7. The network security group allows only 443, plus 80 for the ACME certificate challenge.
  8. Rule 200 denies all other inbound traffic, and there is no SSH rule. Caddy publishes only the realm and resources paths.

Step 2 · Create the SAML client in Keycloak

  1. Step 2: in realm cmp-pdf, create a SAML client whose Client ID equals the Issuer Entra sends: the tenant URL, trailing slash included.
  2. Redirect URI: the Entra ACS, https://login.microsoftonline.com/login.srf. Leave IdP-initiated SSO empty: Entra starts the flow.
  3. Name ID format: persistent, and force it. Entra requires a persistent NameID from a SAML identity provider.
  4. Force POST binding: the signed response always returns to Entra by HTTP-POST.
  5. Sign both the documents and the assertions, using RSA_SHA256.
  6. Client signature required stays off: Entra does not sign the authentication requests it sends.
  7. Add a User Property mapper: email to the attribute http://schemas.xmlsoap.org/ws/2005/05/identity/claims/emailaddress.
  8. Entra requires this claim. Without it, sign-in fails with AADSTS5000819.

Step 3 · Check the SAML metadata

  1. Step 3: fetch the IdP metadata from https://sso.contoso.com/realms/cmp-pdf/protocol/saml/descriptor. The entityID is the realm URL.
  2. It carries the realm signing certificate and offers the persistent NameID format.
  3. SingleSignOnService is …/protocol/saml. Entra uses it as the passive authentication endpoint.
  4. The admin console is not published: the admin path returns 404 from the internet.
  5. configure-cmp-federation.ps1 is a preview by default: it validates the public metadata and writes nothing to the tenant.
  6. It prints the exact Entra inputs: Issuer URI, passive sign-in endpoint, metadata URL and the signing certificate.
  7. It also lists what Entra expects back: tenant audience, login.srf ACS, persistent NameID and the email claim.
  8. ssoVerified is false: a preview proves the inputs, not a working sign-in.

Step 4 · Add the Domainless SAML IdP in Entra ID

  1. Step 4: in the Microsoft Entra admin center, browse to Entra ID › External Identities › All identity providers.
  2. Select the Custom tab, then Add new › SAML/WS-Fed. Sign in as at least External Identity Provider Administrator.
  3. Display name: CMP Keycloak SSO. Identity provider protocol: SAML.
  4. Tick Domainless: Entra then does no domain check of the user’s email. Leave the domain empty; only one such IdP per tenant.
  5. Choose Input metadata manually. Issuer URI: the realm URL, https://sso.contoso.com/realms/cmp-pdf.
  6. Passive authentication endpoint: …/protocol/saml. Certificate: the Base64 signing certificate from the metadata.
  7. Add the metadata URL: Entra can then renew the signing certificate automatically when it expires.
  8. Save. CMP Keycloak SSO appears on the Custom tab: protocol SAML, no domains, certificate expiry shown.
  9. The policy can take 5–10 minutes to take effect. Do not redeem an invitation during that window.
  10. Open the provider again: Domainless is ticked.
  11. No domain is listed. The script’s Graph check reports Domainless as requiring admin center confirmation, so confirm it here.
  12. -Verify reads the federation configurations through Microsoft Graph and compares issuer, protocol, endpoint and certificate.
  13. configurationMatched is true for the Keycloak issuer.
  14. ssoVerified stays false. A saved trust is configuration; the proof is a real guest sign-in.

Step 5 · Invite the guest, MFA and Azure RBAC

  1. Step 5: build the invitation redirect URL with domain_hint equal to the Keycloak Issuer URI.
  2. Learn requires domain_hint = Issuer URI. The exact URL composition is still a PoC item to validate in your tenant.
  3. New-MgInvitation creates the guest. Until it is redeemed, the status is PendingAcceptance.
  4. Grant Azure RBAC at the smallest scope: Reader on rg-cmp-sso-indonesia-poc, deployed from a Bicep template.
  5. Require MFA for guests with Conditional Access. Azure mandatory MFA also applies to Azure portal sign-ins.

Step 6 · Test and troubleshoot

  1. Step 6: test in a private window with the browser developer tools recording. Decode the SAMLRequest with tools/saml_decode.py.
  2. Check that the Issuer equals the Keycloak client ID exactly, and that the request carries no signature.
  3. Then decode the SAMLResponse posted to login.srf and read the summary.
  4. Expected shape: the Issuer is the realm URL, and the whole Response is signed.
  5. The assertion is signed too, and its NameID is persistent.
  6. The recipient is the Entra ACS, https://login.microsoftonline.com/login.srf.
  7. The audience is the Contoso tenant URL, which is also the Keycloak client ID.
  8. The emailaddress attribute carries the guest’s email.
  9. In the PoC, tests T1 and T2 pass. T3 to T8 (redemption, portal sign-in, MFA, authorization) are still open.

Operate and recap

  1. Operate: add a new realm signing key that is not active yet.
  2. In the change window, activate it and confirm the metadata publishes the new certificate.
  3. Update the federation certificate in Entra straight away: an early rotation is not renewed automatically.
  4. After a verified sign-in with the new key, make the old key passive, then remove it.
  5. Recap: Keycloak on Azure is proven. The SAML client, the Entra IdP, the guest and RBAC are configured, not yet end to end.
  6. Next: guest redemption and Azure portal sign-in with MFA. The full guide, scripts and test plan are on this site.
Transkrip Bahasa Indonesia

Intro

  1. Panduan ini membangun trust SAML 2.0 yang memungkinkan pengguna Keycloak login ke Azure sebagai tamu B2B Contoso.
  2. Contoso adalah perusahaan fiktif. Layar PoC adalah tangkapan yang sudah disanitasi; layar ilustratif diberi label.

How the connection works

  1. Ada dua trust. Trust A: frontend CMP memakai Keycloak untuk login melalui OpenID Connect.
  2. Trust B yang dibangun di video ini: Microsoft Entra ID mempercayai Keycloak sebagai identity provider SAML 2.0.
  3. Tidak ada penerusan token: CMP hanya membuka tautan portal khusus tenant. Entra mengautentikasi tamu sendiri melalui Trust B.
  4. Hanya pertama kali: tamu membuka undangan. Redirect URL-nya membawa domain_hint = Issuer URI Keycloak.
  5. Karena IdP-nya Domainless, Entra mengarahkan berdasarkan Issuer URI tersebut dan tidak memeriksa domain email.
  6. Setiap login: tamu membuka Azure portal dengan tenant Contoso di URL-nya.
  7. Entra mengalihkan browser ke endpoint SAML Keycloak dengan AuthnRequest. Issuer-nya URL tenant; permintaan ini tidak ditandatangani.
  8. Keycloak mencari client yang ID-nya sama dengan Issuer tersebut, lalu memakai ulang sesi SSO atau meminta pengguna login.
  9. Keycloak membangun assertion: NameID persistent, klaim email, dan tenant Contoso sebagai audience.
  10. Keycloak mengembalikan form auto-POST; browser mengirim SAMLResponse bertanda tangan ke login.microsoftonline.com/login.srf.
  11. Entra memvalidasi tanda tangan, issuer, audience, recipient, dan waktu, lalu menemukan tamu melalui asosiasi IdP eksternalnya.
  12. Pada penggunaan pertama Entra menampilkan consent, lalu registrasi atau tantangan MFA di tenant Contoso, dan Conditional Access.
  13. Entra menerbitkan token untuk portal, dan Azure RBAC menentukan apa yang dapat dilihat tamu.

Step 1 · Deploy Keycloak on Azure

  1. Langkah 1: deploy-sso.ps1 bekerja bertahap. Validate -Offline mengompilasi tujuh template Bicep SSO: tanpa login, tanpa panggilan cloud.
  2. Validate lalu memeriksa akun, resource provider, SKU VM, dan kuota di Indonesia Central. Sifatnya read-only.
  3. Apply meminta konfirmasi, lalu membuat resource SSO yang terisolasi di rg-cmp-sso-indonesia-poc.
  4. Verify membuktikan HTTPS, issuer, dan URL metadata SAML. identityLogin tetap NOT VERIFIED: itu memerlukan login sungguhan.
  5. Tangkapan PoC: VM Keycloak berjalan di Ubuntu 24.04 dengan ukuran Standard D2s v5 di Indonesia Central.
  6. PoC memakai label DNS Azure ini untuk HTTPS; panduan ini menuliskan origin Keycloak sebagai sso.contoso.com.
  7. Network security group hanya mengizinkan port 443, ditambah port 80 untuk tantangan sertifikat ACME.
  8. Aturan 200 menolak semua trafik masuk lainnya, dan tidak ada aturan SSH. Caddy hanya memublikasikan path realm dan resources.

Step 2 · Create the SAML client in Keycloak

  1. Langkah 2: di realm cmp-pdf, buat client SAML dengan Client ID yang sama dengan Issuer dari Entra: URL tenant, termasuk garis miring di akhir.
  2. Redirect URI: ACS milik Entra, https://login.microsoftonline.com/login.srf. Biarkan IdP-initiated SSO kosong: Entra yang memulai alur.
  3. Format Name ID: persistent, dan paksakan. Entra mewajibkan NameID persistent dari identity provider SAML.
  4. Force POST binding: respons bertanda tangan selalu kembali ke Entra melalui HTTP-POST.
  5. Tandatangani dokumen sekaligus assertion, menggunakan RSA_SHA256.
  6. Client signature required tetap nonaktif: Entra tidak menandatangani permintaan autentikasi yang dikirimnya.
  7. Tambahkan mapper User Property: email ke atribut http://schemas.xmlsoap.org/ws/2005/05/identity/claims/emailaddress.
  8. Entra mewajibkan klaim ini. Tanpanya, login gagal dengan AADSTS5000819.

Step 3 · Check the SAML metadata

  1. Langkah 3: ambil metadata IdP dari https://sso.contoso.com/realms/cmp-pdf/protocol/saml/descriptor. entityID-nya adalah URL realm.
  2. Metadata ini memuat sertifikat penandatanganan realm dan menawarkan format NameID persistent.
  3. SingleSignOnService adalah …/protocol/saml. Entra memakainya sebagai passive authentication endpoint.
  4. Admin console tidak dipublikasikan: path admin mengembalikan 404 dari internet.
  5. configure-cmp-federation.ps1 secara default hanya preview: memvalidasi metadata publik dan tidak menulis apa pun ke tenant.
  6. Skrip mencetak input Entra yang tepat: Issuer URI, endpoint passive sign-in, URL metadata, dan sertifikat penandatanganan.
  7. Skrip juga mencantumkan yang diharapkan Entra: audience tenant, ACS login.srf, NameID persistent, dan klaim email.
  8. ssoVerified bernilai false: preview membuktikan input, bukan login yang berhasil.

Step 4 · Add the Domainless SAML IdP in Entra ID

  1. Langkah 4: di Microsoft Entra admin center, buka Entra ID › External Identities › All identity providers.
  2. Pilih tab Custom, lalu Add new › SAML/WS-Fed. Login minimal sebagai External Identity Provider Administrator.
  3. Display name: CMP Keycloak SSO. Identity provider protocol: SAML.
  4. Centang Domainless: Entra tidak memeriksa domain email pengguna. Biarkan domain kosong; hanya satu IdP seperti ini per tenant.
  5. Pilih Input metadata manually. Issuer URI: URL realm, https://sso.contoso.com/realms/cmp-pdf.
  6. Passive authentication endpoint: …/protocol/saml. Certificate: sertifikat penandatanganan Base64 dari metadata.
  7. Tambahkan URL metadata: Entra dapat memperbarui sertifikat penandatanganan secara otomatis saat kedaluwarsa.
  8. Simpan. CMP Keycloak SSO muncul di tab Custom: protokol SAML, tanpa domain, dan tanggal kedaluwarsa sertifikat terlihat.
  9. Kebijakan ini bisa memerlukan 5–10 menit untuk berlaku. Jangan menebus undangan selama jeda itu.
  10. Buka kembali provider tersebut: Domainless tercentang.
  11. Tidak ada domain yang terdaftar. Pemeriksaan Graph dari skrip menandai Domainless perlu dikonfirmasi di admin center, jadi pastikan di sini.
  12. -Verify membaca konfigurasi federasi melalui Microsoft Graph dan membandingkan issuer, protocol, endpoint, dan sertifikat.
  13. configurationMatched bernilai true untuk issuer Keycloak.
  14. ssoVerified tetap false. Trust yang tersimpan hanyalah konfigurasi; buktinya adalah login tamu yang sesungguhnya.

Step 5 · Invite the guest, MFA and Azure RBAC

  1. Langkah 5: susun redirect URL undangan dengan domain_hint yang sama dengan Issuer URI Keycloak.
  2. Learn mewajibkan domain_hint = Issuer URI. Komposisi URL yang tepat masih PoC item yang perlu divalidasi di tenant Anda.
  3. New-MgInvitation membuat akun tamu. Sampai undangan ditebus, statusnya PendingAcceptance.
  4. Berikan Azure RBAC pada cakupan terkecil: Reader pada rg-cmp-sso-indonesia-poc, di-deploy dari template Bicep.
  5. Wajibkan MFA untuk tamu melalui Conditional Access. MFA wajib dari Azure juga berlaku untuk login ke Azure portal.

Step 6 · Test and troubleshoot

  1. Langkah 6: uji di jendela privat dengan developer tools browser merekam. Dekode SAMLRequest dengan tools/saml_decode.py.
  2. Periksa bahwa Issuer sama persis dengan client ID Keycloak, dan permintaan tidak membawa tanda tangan.
  3. Lalu dekode SAMLResponse yang dikirim ke login.srf dan baca ringkasannya.
  4. Bentuk yang diharapkan: Issuer adalah URL realm, dan seluruh Response ditandatangani.
  5. Assertion juga ditandatangani, dan NameID-nya persistent.
  6. Recipient-nya adalah ACS Entra, https://login.microsoftonline.com/login.srf.
  7. Audience-nya adalah URL tenant Contoso, yang juga menjadi client ID Keycloak.
  8. Atribut emailaddress membawa email tamu.
  9. Di PoC, uji T1 dan T2 lulus. T3 sampai T8 (penebusan undangan, login portal, MFA, otorisasi) masih terbuka.

Operate and recap

  1. Operasional: tambahkan kunci penandatanganan realm baru yang belum aktif.
  2. Pada jendela perubahan, aktifkan kunci itu dan pastikan metadata memublikasikan sertifikat baru.
  3. Segera perbarui sertifikat federasi di Entra: rotasi sebelum kedaluwarsa tidak diperbarui otomatis.
  4. Setelah login dengan kunci baru terverifikasi, jadikan kunci lama passive, lalu hapus.
  5. Ringkasan: Keycloak di Azure sudah terbukti. Client SAML, IdP Entra, tamu, dan RBAC sudah dikonfigurasi, belum end-to-end.
  6. Berikutnya: penebusan undangan tamu dan login Azure portal dengan MFA. Panduan lengkap, skrip, dan rencana uji ada di situs ini.
